HomeControl: Secure Remote AV & Audit

Personal homelab build  •  Sanitized public case study
REQUEST → AUTHORIZE → CAPTURE → STREAM → AUDIT

The goal was not simply to make a camera feed work. It was to make remote access deliberate, private, observable, and easy enough to use every day.

HomeControl started with a practical problem: I wanted to be able to remotely turn on a camera and microphone attached to my primary Windows workstation, view and listen from my phone, then turn everything back off when I was finished.

The technical challenge was not getting video onto a screen. The interesting part was deciding how to expose that capability without opening a camera service to the public Internet, how to keep capture off until requested, how to make the controls usable, and how to retain enough audit information to know what actually connected.

Public-safe version: private IP addresses, internal DNS names, account identifiers, tailnet addresses, exact firewall source rules, and other environment-specific details are intentionally omitted. The architecture and engineering decisions are preserved.

The Design Goal

I wanted the normal resting state to be simple: the streaming service is ready, but the camera and microphone are off. When I deliberately request access, the capture process starts, publishes into the local streaming stack, and becomes available locally or through the approved remote path.

That led to a design with several small components instead of one large exposed application.

A separate internal path connects the same control service to my self-hosted Homepage dashboard. This lets me use the same ON, OFF, VIEW, and AUDIT actions from the LAN without weakening the remote boundary.

Keep Capture Off Until It Is Requested

MediaMTX stays available as the media server, but FFmpeg is the component that owns the physical camera and microphone capture. The Python controller starts FFmpeg only when Remote AV is turned on and keeps a handle to that process.

When the session is finished, the controller sends FFmpeg its normal quit command through stdin instead of routinely killing the process. That change mattered more than it sounds: forced process termination had produced long, inconsistent shutdown times, while graceful shutdown reduced stop time to well under a second in normal testing.

Choose Reliability Over the Flashiest Protocol

I initially wanted a near-real-time WebRTC viewer. The media stack could produce WebRTC, but browser-side ICE negotiation was not consistently reliable in this environment.

Rather than leave the system in a fragile half-working state, I switched the remote viewer to HLS using fragmented MP4. I also changed the remote Python gateway from buffering entire media responses to forwarding them in chunks as they arrived.

That tradeoff produced a remote delay of roughly 3–5 seconds, but the stream became dependable. For this project, a few seconds of latency was a better result than sub-second latency that sometimes failed to connect.

Do Not Put the Camera on the Public Internet

The remote side is intentionally private. The workstation does not rely on router port forwarding for this service, and the project does not use a public Tailscale Funnel.

Instead, an approved mobile device reaches a tailnet-only HTTPS endpoint. Tailscale Serve forwards that connection to a gateway bound only to localhost on the Windows machine. The remote policy is intentionally narrow: the approved endpoint is allowed to reach only the HTTPS entry point required by HomeControl.

The important design idea is that the remote gateway is not simply another web server listening on every interface. It is reachable because a trusted private access layer deliberately hands traffic to it.

Layer the Local Pieces Too

The local environment uses internal DNS and a reverse proxy so the dashboard can refer to readable service names rather than embedding raw addresses everywhere. Windows Firewall restricts the control API to the specific internal systems that need it.

The media path and the control path are also separate. That separation made troubleshooting easier because I could independently ask: Is the controller healthy? Is capture running? Is the stream server ready? Is the viewer reachable?

Make Security Visible

Once the remote path worked, I did not want security to disappear into configuration files. The Homepage card now includes an Audit status field alongside Remote AV, Capture, and Stream Server.

An expected connection shows a normal green state. If the application records a different remote identity or endpoint than the one I expect, the dashboard changes to a CHECK state so that the abnormal condition is visible without opening a database.

Keep the Raw Evidence, Show the Useful Version

HomeControl writes audit records into SQLite. The detailed data includes timestamps, request paths, result codes, remote identity information, user-agent details, and other fields useful during troubleshooting.

That is useful for evidence, but it is not what I want to read every day.

I added a separate audit-history page that reduces the raw records to the information I actually care about:

Connections

Device classification • date • local connection time • local disconnect time

Attempted / failed access

Device classification • date • local time • result

The detailed database remains underneath the clean interface. That pattern became one of my favorite parts of the project: preserve the evidence, but design the operational view around the decisions a person actually needs to make.

Noise Is Not the Same as a Security Event

Browsers generate harmless extra requests—favicons, speculative fetches, and ordinary 404s. Treating all of that as suspicious would make the audit screen noisy enough that it would stop being useful.

The clean history therefore suppresses known low-value browser noise from the approved device while retaining meaningful failed or unexpected application-level access.

There is also an important visibility boundary: if the private network layer rejects a connection before it ever reaches HomeControl, the application cannot log a request it never received. The audit database represents activity that reached the application boundary, not every packet rejected elsewhere in the stack.

Automatic Startup Without Automatic Capture

The controller and remote gateway are launched through Windows Scheduled Tasks at user logon. That allows the control plane and stream server to return after a normal restart while still leaving the camera and microphone off.

The intended post-login state is:

REMOTE AV: OFF  •  CAPTURE: OFF  •  STREAM SERVER: READY  •  AUDIT: OK

What Changed Between the First Working Version and the Useful Version

The project evolved through several small but important changes:

  • Moved RTSP ingest to localhost instead of exposing it unnecessarily.
  • Kept MediaMTX persistent while making physical capture on-demand.
  • Replaced forced FFmpeg termination with graceful process shutdown.
  • Abandoned unreliable WebRTC behavior in favor of stable HLS/fMP4 delivery.
  • Changed the remote gateway from full-response buffering to streaming chunks.
  • Restricted the remote path to an approved mobile endpoint and HTTPS entry point.
  • Added SQLite audit logging instead of relying only on console output.
  • Separated detailed forensic records from a clean human-readable audit view.
  • Integrated operational status and controls into Homepage.

What I Took Away

The biggest lesson was that a working prototype and a trustworthy system are not the same thing.

The first success was seeing video remotely. The more valuable work came afterward: reducing exposure, tightening the remote path, improving process behavior, measuring latency, choosing a more reliable protocol, separating local and remote concerns, recording access, and making the result easy to understand from one dashboard card.

The finished system is useful because the security and operational behavior are part of the design, not features added after the camera feed worked.

This public case study is intentionally sanitized. The private build documentation contains the environment-specific ports, addresses, scheduled-task settings, recovery steps, and reproduction details needed to rebuild the system.
