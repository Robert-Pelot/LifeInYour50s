From CRUD Endpoints to an API Architecture

Coursework project  •  Portfolio case study
REQUEST → CONTROLLER → SERVICE → REPOSITORY → SQL

The endpoint is only the visible edge of the system. The interesting work is what has to happen behind it.

At first, a REST API can feel like a collection of verbs and URLs: GET something, POST something new, PUT a change, DELETE what no longer belongs.

That was the starting point of this project. I was building an API around courses, core goals, and course offerings, and the early goal was straightforward: make the endpoints work.

What changed for me was realizing that a working endpoint is not the same thing as a well-designed system.

I started the project thinking mostly about whether an endpoint returned the right result. I finished it thinking much more about how a change moves through a system.

CRUD Was the Starting Point

The first version covered the familiar API operations: retrieve courses, retrieve core goals, add records, edit them, delete them, and follow the relationships between courses and goals. Postman made it easy to see whether the HTTP side of the application was behaving the way I expected.

One early design choice forced me to think beyond simply matching an assignment specification. Two requested operations would have collided at the same route, so I separated the behavior instead of pretending one URL could represent two different jobs. In another case, I chose a POST operation that could assign a list of courses to a goal rather than limiting the operation to one course at a time.

Those were small decisions, but they were the first signs that API design is really about expressing intent clearly.

Then One Feature Started Touching Six Places

The repository-layer work made the architecture much more concrete. Adding a new feature was no longer a matter of dropping one more method into a controller.

A complete change could require updates in six places:

  1. the repository interface,
  2. the repository implementation and SQL query,
  3. the service layer,
  4. the service tests,
  5. the controller and HTTP endpoint, and
  6. the service interface.

That was when terms like separation of concerns, repository pattern, and SOLID stopped feeling like vocabulary words. They became a way to understand why the project was organized the way it was.

A layered design does not make change disappear. It gives the change a predictable path.

The Data Model Can Betray the API

The more interesting problems appeared after the basic endpoints worked.

I noticed that a course with no offerings could disappear from the normal course-discovery path. A course that was not connected to a core goal would never appear in goal-based searches. And the original create-course workflow accepted the course itself but gave the caller no way to say which core goal or goals it belonged to.

In other words, the API could successfully create a record that later became difficult to discover through the very searches the application was supposed to support.

That was an important shift in how I looked at the project. The controller was not the application. The database was not the application. The API was the behavior created by all of those pieces working together.

User Stories Forced the Architecture to Grow

After completing the required work, I realized that several searches designed around the user stories still were not exposed through the web API. So I went back and added them.

The API grew to support things such as offerings by semester and department, offerings by core goal and semester, courses matching multiple core goals, goals missing offerings in a semester, and course searches by department. I also added Swagger so the available API surface could be inspected and exercised more easily.

This is where the project stopped feeling like a collection of CRUD demonstrations and started feeling more like an actual service.

Testing Meant More Than Seeing a 200

I also became more deliberate about testing the lifecycle of a change. Adding a course was followed by verifying that it existed. Editing it was followed by verifying the changed data. Deleting it was followed by checking that it was actually gone.

A green status code is useful, but it does not prove the rest of the application still makes sense. The stronger question became: Does this operation behave correctly when viewed through the other features that depend on the same data?

What I Took Away

Before this project, it was easy for me to think of an API primarily as a set of endpoints.

After working through repositories, services, controllers, relationships, tests, and user stories, I see the endpoint as the smallest visible part of the architecture.

The more important skill is understanding how a requirement travels through the layers underneath it—and recognizing when a design that technically works is still creating problems somewhere else.

That is what I took away from this project: software architecture is not about adding layers for their own sake. It is about making change understandable.

Techniques and Tools Demonstrated

This project gave me hands-on experience with the parts of an API that sit behind the endpoint: controllers, service and repository layers, relational data, validation, testing, and the HTTP interface presented to a client. Just as important, it taught me to look for problems that appear only when those pieces interact.
