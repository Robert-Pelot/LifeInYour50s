Diagnosing a Multi-Floor Network

By Robert Pelot  •  September 23, 2026
“NO CONNECTION” IS A SYMPTOM, NOT A DIAGNOSIS.

The failure might be the host, its gateway, a disabled device, the route table, or a policy rule. The useful skill is separating those possibilities.

A host that cannot reach a server does not automatically have a routing problem.

A Cisco Packet Tracer final gave me a compact exercise in working through that idea. The topology represented a multi-floor network with routed subnets, switching, dynamic routing, an internet-facing path, access-control rules, and remote administration.

The point of the public case study is not the worksheet itself. What matters is the troubleshooting process: identify the failure domain, gather evidence, and avoid changing configuration until the evidence points somewhere.

Start with the obvious faults

The first two problems were simple but important. FLOOR2 was not turned on, and PC36 did not have a default gateway configured.

Those are different failures, but they can produce the same user-facing complaint: traffic does not get where it is supposed to go. A routing protocol cannot compensate for an unavailable network device, and a correctly routed network cannot help a host that does not know where to send off-subnet traffic.

VERIFY THE SIMPLE LAYERS FIRST.

Device state, host addressing, gateway configuration, routing, and policy are separate places where the same connectivity symptom can originate.

Follow the packet path

The next question was how traffic from a workstation would move toward the web server. Working through that path meant distinguishing switching from routing instead of counting every device as a hop.

It also raised a more useful question than “Can I ping it?”: what should happen at each layer between the source and destination?

Read the routing table before changing the network

The FLOOR3 routing table showed directly connected networks, routes learned through OSPF, and a gateway of last resort. That is useful evidence because it shows what the router actually knows rather than what I assume it should know.

The exercise also identified OSPF as the dynamic routing protocol and used a router ID of 33.33.33.33 for FLOOR3. Those details help confirm that the routing plane is not just present but understandable.

A route can exist and traffic can still be blocked

PC23 and PC24 could not reach the web server because an extended access-control list was intentionally blocking IP traffic from their subnet to the target host.

That is a very different diagnosis from “the router does not know where the server is.” The network can have a valid path and still be configured not to forward the traffic.

That distinction carries directly into real infrastructure work: reachability and authorization are not the same thing. Troubleshooting has to verify both the path and the policy.

Verify the management plane too

The final checks included switch management addressing, default-gateway information, and whether SSH was configured for remote administration. The exercise confirmed SSH version 2 was enabled.

Those checks are part of understanding the system, not an afterthought. A network has to be reachable, routable, permitted, and manageable.

What this demonstrates

  • Basic Cisco IOS inspection and interpretation
  • Understanding of default gateways and routed versus switched paths
  • Recognition of OSPF-learned routes and router-ID information
  • ACL-based traffic filtering and policy troubleshooting
  • Switch management addressing and SSH administration
  • A layered troubleshooting process instead of random configuration changes

What I took away

The useful lesson was not a particular Cisco command. It was the order of operations: check whether the device is available, check the host configuration, inspect the route, inspect policy, and verify the management plane.

Each layer can create the same visible symptom. Each requires a different fix.

The fastest way to troubleshoot a network is to stop treating every connectivity failure as the same problem.

This case study is adapted from an IST 204 Cisco Packet Tracer final. The public version focuses on the troubleshooting process and the networking concepts demonstrated by the exercise rather than reproducing the assignment as a question-and-answer worksheet.
