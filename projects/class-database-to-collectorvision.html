From a Class Database to CollectorVision

Coursework that kept evolving  •  Active personal project
MODEL → POPULATE → PLAN → REBUILD → RECOGNIZE → OPERATE

The interesting part was not finishing the database assignment. It was realizing that the assignment had exposed a problem I still wanted to solve after the class ended.

CollectorVision did not begin as an image-recognition project. It began much more simply: I wanted a structured way to manage a real die-cast collection, and a database course gave me a reason to formalize the problem.

The first version focused on tables, relationships, sample data, and the rules needed to describe cars, brands, condition, rarity, purchases, storage, materials, photos, and sales. What happened afterward is the part that became portfolio-worthy: I kept rebuilding the idea until it became a self-hosted application with a reference catalog, verified collection data, image workflows, OCR, computer vision, review tools, and operational documentation.

What this case study is: a look at how the design evolved. Some early cloud security and backup material was coursework planning rather than proof that every proposed Azure control was deployed. The current CollectorVision architecture described here reflects the working project and its public repository.

1. Start With the Data Model

The original database design was built around a straightforward inventory problem. A car needed relationships to things such as brand, category, condition, rarity, purchase information, storage location, materials, and photos. Some relationships were one-to-many; others, such as materials, required a many-to-many design.

That first exercise taught me something that still shapes CollectorVision: if the relationships are vague, the application logic becomes vague too. Before worrying about recognition or automation, I had to decide what the system was actually trying to represent.

2. Populate It With Real Data

The next milestone moved from an ERD and business rules into actual SQL. Lookup tables were populated for manufacturers, conditions, categories, makes, materials, rarity, purchase locations, and storage. Car records referenced those tables instead of repeating the same descriptive text everywhere.

Photos were already modeled as their own records linked to a car, which mattered later. A collection object is rarely represented well by one image, and the idea of one record having multiple useful views eventually became a much larger part of CollectorVision.

Early lesson: normalization was not just an academic requirement. It was what made the data reusable.

Instead of one giant row containing everything about a car, separate tables let the application reuse manufacturers, conditions, categories, storage locations, and photo records consistently.

3. Think Beyond the Database File

A later course milestone asked me to think about what would happen if the MySQL database were operated in Azure. I developed a security and backup strategy covering identity and access, role separation, firewall rules, TLS, encryption, auditing, monitoring, backup retention, restore testing, disaster recovery, and operational review.

That document was a design plan, not evidence that every control was implemented exactly as written. But it pushed the project beyond schema design. I had to think about a database as a service that needs access control, recoverability, monitoring, and maintenance—not simply as a set of tables that return correct queries.

DATA THAT WORKS IS NOT THE SAME AS DATA YOU CAN TRUST TO SURVIVE.

Security, backup, restore testing, and operational visibility became part of the design conversation.

4. The Course Model Was Useful—but Not the Final Architecture

As I continued working with the collection, the limits of the original model became obvious. A simple car record was not enough to represent the difference between a casting, a specific release, a physical variation, reference information found elsewhere, and an item I actually own.

CollectorVision eventually separated those concepts instead of forcing them into one table.

IdentityManufacturer
→
VehicleCasting
→
Release contextRelease
→
Physical detailsVariation
→
OwnershipCollection item

This was one of the biggest architectural changes. Release-year information belongs at the release level. Physical color, wheel, base, packaging, and related differences belong at the variation level. Ownership belongs to the specific variation I actually possess.

5. Reference Knowledge Became Its Own Layer

The next problem was recognition. To identify a vehicle from a photograph, the system needs far more reference information than I would ever personally own.

That led to a separate Reference Catalog: a larger knowledge and staging layer that can hold source-derived records, multiple images, source provenance, import history, component details, and links to verified production records when a match has been confirmed.

The key design rule became:

PROMOTION IS LINKAGE, NOT MIGRATION.

Reference information remains available as provenance and recognition material even after a verified casting, release, or variation has been created.

That prevents the application from throwing away the evidence that helped establish the record in the first place.

6. Images Became Data, Not Decoration

The original class database already treated photos as separate records, but CollectorVision pushed that idea much further. Reference entries can have multiple images with different roles such as card front, card back, loose car, packaging, detail, or general reference.

That mattered because different recognition problems need different views. A card-front image may be useful for package identification, while a loose-car image is more useful for shape and color matching.

7. Recognition Became a Pipeline, Not a Magic Button

CollectorVision now uses multiple recognition strategies depending on the kind of image being analyzed. Package workflows can use manufacturer-specific OCR and metadata analysis. Loose-car workflows can use SIFT, Bag of Visual Words, color-assisted matching, and fallback searches against reference imagery.

I deliberately did not make recognition the final authority. Automated matching narrows and ranks possibilities; the user confirms the identity before collection-changing actions are applied.

InputPhoto
→
AnalysisOCR / visual features
→
SearchReference candidates
→
DecisionUser confirms
→

Recognition suggests; the user confirms; CollectorVision then applies the established promotion and collection logic.

8. It Became an Operated System

The current application is self-hosted in an Ubuntu LXC and uses FastAPI, Jinja, SQLite, OpenCV, Tesseract OCR, systemd services, and NAS-backed image and report storage.

The project also has operational concerns that did not exist in the first assignment: service startup, health checks, recognition-index rebuilds, file storage boundaries, review queues, provenance, backups, recovery, and documentation that has to stay synchronized with the live application.

Then: design a relational database and populate it correctly.

Now: operate a self-hosted system that separates reference knowledge, verified production data, personal ownership, image evidence, and recognition indexes.

What Changed Between the First Version and Today

  • A general car record became a hierarchy of casting, release, variation, and collection ownership.
  • One database became separate layers for reference knowledge and verified production data.
  • Photos evolved into multi-role image evidence used by recognition workflows.
  • Manual cataloging gained OCR, SIFT, BoVW, color-assisted matching, and guided review.
  • Coursework security and backup planning evolved into real operational thinking about storage, services, recovery, and provenance.
  • A class deliverable became a system I still actively change because I actually use it.

What I Took Away

The biggest lesson is that the first data model does not have to be the final one.

The original coursework was valuable because it forced me to define relationships and make the collection concrete. But the real learning happened when I kept using the idea and discovered where the model was too simple, where the workflow was too manual, and where recognition needed better evidence and review.

CollectorVision became interesting when the assignment stopped telling me what to build.

That is why I still consider it one of my most important projects. It connects database design, systems thinking, Python development, computer vision, Linux administration, operational documentation, and a real problem I actually care about solving.
