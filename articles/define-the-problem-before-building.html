Before I Built the Solution, I Had to Define the Problem

By Robert Pelot  •  September 16, 2026
PROBLEM → REQUIREMENTS → TEST

If I cannot explain how I will test a requirement, I probably have not defined it clearly enough.

One of the easiest mistakes to make in technology is to start building too soon.

You have an idea. You can already picture the screens, the database, the code, and maybe even the finished product. The temptation is to open an editor and start making something happen.

That is exactly where I was with my Health Data Readiness Workbench.

I already knew roughly what I wanted it to do: take healthcare-related data, examine it for quality problems, and help someone decide whether the data was actually ready for analysis. But during my Information Systems capstone, I was forced to do something much less exciting before I could build anything.

I had to define the problem precisely enough that I could tell whether the eventual solution actually solved it.

That turned out to be one of the most useful parts of the project.

A Problem Is More Than a Feature List

At first, it would have been easy to describe the project as a data-cleaning application. That description was not wrong, but it was not very useful either.

The real problem was more specific: healthcare analysts can receive datasets with missing values, duplicate identifiers, inconsistent formats, impossible dates, broken relationships between tables, and other defects that make the data less useful for analysis.

If those problems are not found early, they can weaken dashboards, reports, statistical analysis, claims analysis, or predictive models. A system that merely opens a CSV file or produces a nice chart does not solve that problem.

So I reframed the project around a different question:

Can I give someone a repeatable way to understand the condition of a dataset before they trust it for analysis?

That question gave the project a boundary. The Workbench did not need to prove that every medical value was clinically true. It did not need to replace Tableau, R, Python, or other analytical tools. It needed to identify defined problems, explain what was found, show which records were affected, and document limitations before downstream analysis began.

Breaking a Big Idea into Smaller Problems

Once I had a clearer problem statement, I realized that “data readiness” was not one problem at all. It was a collection of smaller problems that depended on one another.

The system had to import data and understand its structure. It needed rules for detecting missing, duplicated, malformed, inconsistent, or relationally invalid values. It needed to record exactly what each rule found, summarize the impact, let users review the results, and export them. Because the subject was healthcare data, security and accountability had to cut across the entire design.

The most important component became the validation rule engine. That was the point where the project stopped being a generic file viewer and became a real data-readiness system.

A vague warning such as “your data has problems” is not very useful. A specific finding such as “this encounter ends before it begins” or “this record references a patient that does not exist” gives someone something they can investigate.

Requirements Forced Me to Stop Hand-Waving

Writing requirements was another exercise that looked academic at first and became surprisingly practical.

It is easy to say that software should be secure, fast, accurate, and easy to use. Those words sound good, but they are difficult to test.

So I had to turn them into things I could measure: preserve imported source data unchanged, require authentication for non-public pages, restrict administrative functions by role, record defined actions in an audit trail, and make the core workflow usable without developer assistance.

I also set performance and validation targets for the capstone test environment. They were not industry-standard claims; they were acceptance targets that gave me something concrete to test against.

That changed the way I thought about requirements. A good requirement is not there to make a document look professional. It creates a future yes-or-no question: did the system actually do what I said it would do?

If I cannot explain how I will test a requirement, I probably have not defined it clearly enough.

Testing with Problems I Created on Purpose

One of my favorite parts of the design was the test strategy.

Public and synthetic healthcare datasets are useful because they let me build and test without exposing real patient information. But a dataset prepared for public use may already be fairly clean, which is awkward when the software is supposed to find bad data.

My solution was to keep an untouched source dataset, make a separate test copy, and deliberately corrupt the copy. I could remove required values, create duplicate identifiers, insert impossible dates, or break relationships between records. Alongside that file, I would keep a defect manifest describing exactly what I changed.

Now I had ground truth.

Instead of saying, “The application found a lot of errors, so it must be working,” I could compare known defects with detected defects. I could count what the system found, what it missed, and what it flagged incorrectly.

That is a much stronger test than simply looking at the screen and deciding the results seem reasonable.

Security Had to Be Part of the Architecture

The healthcare context affected the design from the beginning.

For the capstone, I planned to use synthetic or public-use data rather than real patient data. I also deliberately avoided claiming that a student project was “HIPAA compliant.” What I could do was apply sound principles such as controlled handling, role-appropriate access, auditability, preservation of source data, and local processing by default.

One requirement was especially important to me: imported row-level data should not be sent to a third-party AI or web service as part of the normal validation workflow.

That decision came from both my cybersecurity background and the health-informatics side of the project. Convenience is not a good enough reason to move sensitive information into a system that was never designed or approved to receive it.

Security was therefore not a final feature to add once the application worked. It was part of what “working correctly” meant.

The Hardest Question: Should I Build It at All?

There was one more uncomfortable question I had to answer before I could justify building my own tool:

Does something already exist that solves this problem?

I compared my proposed Workbench with OpenRefine, a mature open-source tool for exploring, transforming, standardizing, and cleaning messy data.

That comparison forced me to stop treating “custom-built” as automatically better. OpenRefine was broader in several general-purpose transformation areas, while my planned Workbench was narrower and focused on explicit healthcare-data validation, readiness metrics, controlled testing, role-based workflow, and auditability.

I used a weighted decision matrix to compare those problem-specific needs. The planned Workbench scored better against my narrow criteria, while OpenRefine clearly did better in general transformation breadth.

The useful part was not the score. The useful part was that the score had to be revisited after implementation. If I failed to build a feature or it did not pass its acceptance test, the Workbench's rating had to come down.

That made the decision testable instead of self-justifying.

What I Took Away from the Exercise

Before this project, I tended to think of problem analysis and requirements as the paperwork that came before the interesting part.

I do not see them that way anymore.

The analysis changed what I was building. It narrowed the scope. It exposed dependencies. It made security part of the architecture. It gave me a test strategy. It forced me to define success in measurable terms. And it made me compare my idea with an existing tool before assuming that writing my own software was justified.

Most importantly, it gave me a way to recognize failure.

If a project can only succeed because I get to redefine success after I finish it, then I never really tested the idea.

Defining the problem first gave me something much better than a feature list.

It gave me a standard the finished system would have to meet.

This article grew out of the problem-analysis and requirements work for my Information Systems capstone, the Health Data Readiness Workbench. The original coursework used formal software-engineering methods; this version focuses on how those methods changed the way I approached the project.
